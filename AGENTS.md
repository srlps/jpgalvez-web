# AGENTS.md

## Project
Static reconstruction of `transportesjpgalvez.com` (Transportes e Inversiones Jeanpierre S.A.C.), a company site that went offline after the domain was lost. The original source code no longer exists — the only reference is the Wayback Machine capture:

- https://web.archive.org/web/20231107032817/http://transportesjpgalvez.com/

**Phase 1 (done)**: rebuild the site as-is from the archive capture — same sections, text, images and page structure, no redesign. See EXTRACTION.md for how the raw HTML/assets were pulled from the archive, and "Source/dist architecture" below for how that raw HTML was then migrated into the current Astro source.
**Phase 2 (in progress, scope confirmed with owner 2026-09-28)**: modernize/redesign the visual style, and add a small admin console so the owner can upload images and add new clients/testimonials without a developer editing files by hand. This requires a real backend for the first time — see "Firebase backend (Phase 2)" below for the chosen stack and its current setup status.

**Admin console split into its own project (2026-09-29)** — the owner decided the admin console should live on a separate `admin` subdomain rather than under `/new/admin/`, and since it would be on its own origin anyway, asked for it to become a React SPA instead of the vanilla-JS Astro page it started as. This repo now contains **2 independent npm projects** — see "Admin console (admin/, separate project)" below.

**Redesign preview lives under `/new/`** (added 2026-09-28) — a full parallel site so the owner can compare old vs. new page by page before approving anything; the current site at `/` is untouched. See "Redesign preview (/new/)" below.

**Redesign constraint (from the owner): no rebranding** — logo, brand name and colors stay as they are; only layout, typography usage, spacing and components modernize. [GUIA-DE-ESTILO.md](GUIA-DE-ESTILO.md) (Spanish) is the source of truth for the redesign's palette (sampled from `logo.png` + existing `site.css`, no new hues), typography (Fjalla One + Open Sans kept), spacing/radius/shadow tokens and component rules. Read it before any visual change; its section 9 lists usage changes still pending owner confirmation. **Brand colors (owner, 2026-10-02): azul, granate and plata `#BBBCBF`** (fleet and uniforms). In `/new/`, **no section background is white** (body and light bands use `--color-plata-claro`; white is only for cards/inputs), plata is the accent for overlines/circles on dark backgrounds, and plata stripes sit under the header and above the footer. Cian is kept (client's choice) for the nav hover/active underline, hero metrics, founding year, testimonial border/quote mark, the Contacto icons/labels and the focus ring. A more drastic version (whole page silver, pure-plata bands, azul contact) was tried and rejected by the user — keep plata changes subtle, don't restructure sections.

## Stack
Static HTML/CSS output for the public site, no client-side framework — this is a brochure/informational site (no client state, no auth on the public pages), so React/Vue add an unneeded client runtime and hurt SEO for zero benefit. Phase 2 adds a Firebase backend (Firestore/Storage) behind an authenticated admin console — see below — but the public pages themselves stay static output from Astro.

**Static-site generator: [Astro](https://astro.build/)**, chosen to compile layouts/partials down to plain HTML with zero client JS runtime by default. Fragments extracted into shared layout/partials (all under `src/`):
- `src/layouts/BaseLayout.astro` — `<head>`, header, footer, and the site-wide CSS/JS imports (see `src/components/Header.astro`, `Footer.astro`)
- `src/components/forms/HomeQuoteForm.astro`, `ContactForm.astro` — the 2 remaining quote/contact form variants ("SOLICITE SU PRESUPUESTO" on Inicio, and Contáctenos' own form). See backend note below. The 4 service subpages' "COTICE SU SERVICIO AHORA" form (`ServiceQuoteForm.astro`/`ServiceQuoteSection.astro`) never worked (no `action`, duplicate `id` bug — see EXTRACTION.md) and was removed rather than kept as a non-functional placeholder.
- `src/components/ServiceNav.astro`, `Cabecera.astro`, `ElegirNos.astro` — smaller fragments reused across the service subpages / Inicio / Nosotros / Clientes.

**Styles/scripts (optimized, no jQuery)**:
- `src/styles/site.css` — the **only** stylesheet. It replaced the 7 theme CSS files (Bootstrap 3, Font Awesome, Owl Carousel, Revolution Slider, Konstruct `style.css`/`shortcode.css`/`responsive.css`), keeping only rules the markup actually uses (the theme CSS was reduced by running PurgeCSS against the built HTML, then hand-merged and verified with pixel diffs against the previous build — desktop renders identically). No inline `style=""` attributes or `<style>` blocks in pages/components: add styles to `site.css`.
- `src/scripts/site.js` — vanilla JS replacing jQuery + all theme plugins; the only behaviors the site used were the sticky header (≥992px), the mobile menu toggle and the "go to top" button. Revolution Slider was replaced by a plain `<img class="banner">` (the slider only ever had one static slide), Font Awesome by an inline SVG (menu icon) and a CSS chevron (go-to-top).
- Some rules in `site.css` intentionally reproduce spacing that the original markup produced through junk elements (empty `<p>`s from nested CMS paragraphs, `<br>` stacks, `&nbsp;` spacer columns), e.g. `h1 + p { margin-top: 20px }` or `.derco { padding-bottom: 200px }` — removing them changes the layout. The three `<br>` in `Header.astro` are also load-bearing (they position the floated menus) and were kept on purpose.

## Source/dist architecture
Source lives under `src/` (Astro components/pages) and `public/` (static assets copied as-is); the buildable site is generated into `dist/` — **never edit `dist/` directly**, it's regenerated and gitignored.

- `npm install` — install dependencies (first time only)
- `npm run dev` — local dev server with live reload (http://localhost:4321)
- `npm run build` — generates the static site into `dist/`
- `npm run preview` — serves the built `dist/` locally, to sanity-check the actual build output

Internal links and asset references use root-absolute paths (`/nosotros/`, `/images/...`) rather than the original archive's relative `../` paths — required by the layout/partial system (the same partial renders at different nesting depths) and idiomatic for Astro's routing, not a visual/content redesign. `astro.config.mjs` sets `trailingSlash: "always"` so `src/pages/nosotros.astro` builds to `dist/nosotros/index.html`, matching the original site's path structure exactly.

## Firebase backend (Phase 2)
Scope confirmed with the owner 2026-09-28: a modernized visual redesign plus a small authenticated admin console (upload images, add clients/testimonials) that the owner can operate without a developer. The owner connected the repo to a Firebase project with **Hosting, Firestore and Storage**. Cloud Functions was tried and then dropped the same day (see below) — email sending stays on Web3Forms, not Functions.

**`firebase init` completed 2026-09-28** — `firebase.json` and `.firebaserc` now exist (project alias `jpgalvez-7a5b3`), so the project has a real deploy target config:
- **Hosting (2 sites, since 2026-09-29)**: `firebase.json`'s `hosting` is an array of 2 targets — `web` (`"public": "dist"`, the Astro landing, target's Hosting site ID is the default `jpgalvez-7a5b3`) and `admin` (`"public": "admin/dist"`, the React SPA in `admin/`, target's Hosting site ID `landing-admin`). `.firebaserc` maps both targets under `targets.jpgalvez-7a5b3.hosting`. **Both sites are deployed (2026-10-01)** on their default Firebase URLs, with no custom domain yet, so the owner can validate the product live; attaching the real domain and the `admin` subdomain from the Firebase console is still pending. No `rewrites`/`cleanUrls` configured on either site; not needed since `astro.config.mjs`'s `trailingSlash: "always"` already emits `<page>/index.html`, which Hosting serves natively for a directory-style request, and the SPA doesn't need client-side routing (single screen, tab state only).
- **Firestore**: region `us-east1`, rules in `firestore.rules`, indexes in `firestore.indexes.json`. **Rules rewritten 2026-09-28** (replacing the 30-day test rule) for the `/new/` admin console: public read only for docs with `publicado == true`, all writes restricted to admins (uid present in `/admins/{uid}`, a collection no client can write — created by hand in the Firebase console), strict per-collection schema validation (`clientes`, `testimonios`, `galeria`; data model documented at the top of the file). `firestore.indexes.json` defines the 3 composite indexes the public queries need (`publicado` + `nombre`/`orden`/`creadoEn desc`). **Rules and indexes are deployed (2026-10-01)**, and so are the Storage rules. The database was wiped and recreated after the owner polished the original client list, and the single testimonial was loaded again afterwards; the data in Firestore is the correct, final set. The owner also exported it and keeps a local backup (see "Full JSON export" below).
- **Storage**: `storage.rules` rewritten the same day: public `get` (no `list`) on `clientes/`, `testimonios/`, `galeria/`; create/update/delete only for admins (cross-service `firestore.exists()` on `/admins/{uid}`), images only (webp/jpeg/png, <5 MB, filename `<docId>-<timestamp>.<ext>`). First deploy asks to grant Storage permission to read Firestore — accept it. Everything else deny-all.
- **Authentication**: required by the admin console (email/password), shared by both the old `/new/` preview (public site) and the new `admin/` SPA — same Firebase project, same `admins/{uid}` doc. Not enabled by `firebase init` — the owner must enable the Email/Password provider, create the admin user, and add a doc `admins/<uid>` in Firestore. **Status (2026-10-01):** a **test admin user** (Email/Password + its `admins/<uid>` doc) is set up and the console works end to end with it: the client logos and the testimonial were loaded through the deployed admin console itself (this doubled as its functional test). Still pending: logging in with a real email, testing the password-recovery flow (the "Olvídé mi contraseña" button in `admin/src/components/Login.tsx` calls `sendPasswordResetEmail`; check the email arrives, the link works and the Firebase email template/sender look right) and setting up the production admin account(s) with the email the client will actually use — then remove or disable the test user.
- **Functions: removed 2026-09-28.** `firebase init` had scaffolded a `functions/` TypeScript codebase (default `setGlobalOptions` boilerplate only, no email-sending function was ever written), but the owner deleted the `functions/` folder outright — Cloud Functions is no longer part of this project's plan. The dangling `functions` block this left behind in `firebase.json` (pointing at a now-nonexistent `source: "functions"`, which would have broken `firebase deploy`) was removed to match. If server-side email sending is revisited later, re-run `firebase init functions` from scratch rather than trying to recreate the deleted folder by hand.
- Practical effect: the project is structurally deployable, and the rules/indexes for the `/new/` admin console are **live** (see above). The owner runs the Firebase CLI directly (dry-run, deploy, enabling Auth); this project's job is to author/review rules and keep docs in sync, not to run `firebase` commands.

## Admin console (admin/, separate project)
Moved out of `/new/admin/` into its own npm project, `admin/`, on 2026-09-29 — the owner wants it deployed on a separate `admin` subdomain (different Firebase Hosting site/target, see "Firebase backend" above), and since it'd be a separate origin anyway, asked for a React rewrite instead of keeping the vanilla-JS version. This is a **second, fully independent npm project** living as a sibling of `src/` at the repo root (own `package.json`, `node_modules`, `tsconfig.json` — NOT an npm workspace, kept fully decoupled on purpose). The root project's `tsconfig.json` excludes `admin/` so Astro's TS tooling doesn't try to type-check it.

- **Stack**: Vite + React 19 + TypeScript, `firebase` JS SDK (`firebase/firestore/lite`, same load-once pattern as `publico.js`). No client-side router — a single screen with `useState`-based tab switching (Clientes/Testimonios/Galería), all 3 panels always mounted, toggled via the `hidden` attribute (preserves state/avoids refetching on tab switch).
- **Commands** (run from `admin/`, or via the root `package.json` convenience scripts `npm run admin:install` / `admin:dev` / `admin:build`): `npm install`, `npm run dev`, `npm run build` (`tsc -b && vite build` → `admin/dist/`), `npm run preview`.
- **Env vars**: `admin/.env` (gitignored, template in `admin/.env.example`) uses the `VITE_FIREBASE_*` prefix (Vite convention) — same Firebase project/credentials as the root `.env`'s `PUBLIC_FIREBASE_*`, just re-declared under Vite's required prefix. Without them, the SPA shows a setup notice instead of the login screen.
- **Functional parity**: same Firebase Auth email/password + `admins/{uid}` check; CRUD for clientes (name, optional logo, destacado, publicado), testimonios (autor, cargo, empresa via cliente link, texto, orden, publicado) and galería (multi-upload, client-side resize to max 1920 px WebP, título/categoría/descripción, publish toggle). The one-click imports of bootstrap seed data (the 360 `clientes.json` names, and the single MM Consultores testimonial) were both removed once the owner manually loaded the real data into Firestore — `admin/src/data/clientes-semilla.json` (2026-09-29) and `admin/src/data/testimonios-semilla.ts` (2026-09-29) were deleted, neither is needed again. DOM built via React (no `dangerouslySetInnerHTML` used).
- **Logo processing (2026-09-29)**: client/testimonial logos go through the same client-side resize+WebP pipeline as gallery photos (`admin/src/lib/imagenes.ts`'s `prepararImagen()`), just with a smaller max side (400 px vs. the gallery's 1920 px) — appropriate since logos only ever render at 56–64 px in the public site.
- **Testimonio "empresa" is a real link to Clientes, not free text (2026-09-29, revised same day)**: `testimonios` docs store a `clienteId` (the linked cliente's Firestore doc ID) instead of an `empresa` string — the company name AND logo shown on the public site come from that cliente doc, not from the testimonio itself (no more separate logo upload for testimonios). `TestimoniosPanel` still offers the same searchable `<input list><datalist>` combobox (typed text matched accent/case-insensitively via `admin/src/lib/texto.ts`'s `normalizar()` against the `clientes` collection) — on submit the matched cliente's `nombre` resolves to its `id`, which is what actually gets stored; submission is blocked if there's no match (message differs when the `clientes` collection is simply empty vs. when the typed text doesn't match anyone). `firestore.rules`' `isValidTestimonio()` enforces the link server-side too (`clienteExiste()` calls `exists()` on `clientes/{clienteId}`), so a testimonio can never point at a nonexistent cliente. Decided to link by ID (rather than only validate the text) because Firestore was still empty for this project at the time, so no migration was needed. The public site (`src/scripts/new/publico.js`) resolves each testimonio's `clienteId` with an individual `getDoc` (few testimonios, cheap) and falls back to showing no company name/logo if that cliente doc doesn't exist or isn't `publicado` (read denied by rules) — so an admin must keep the linked cliente published for its testimonio to show a company/logo.
- **Testimonial static seed removed (2026-09-29)**: once the owner uploaded the real (only) testimonial to Firestore by hand, the static fallback (`src/data/testimonios-iniciales.ts`, `src/components/new/TestimonioCard.astro`) and the admin's one-click import button/seed (`admin/src/data/testimonios-semilla.ts`) were both deleted — `Testimonios.astro` now renders an empty `<ul>` that `publico.js` fills in from Firestore, same treatment already given to the clientes seed import.
- **Clientes `tipo` (empresa / persona natural, 2026-09-30)**: `clientes` docs have an optional `tipo` field (`"empresa"` | `"persona"`; a missing value means `"empresa"` — originally because the ~360 existing docs predated the field, now only a fallback, since the database was recreated 2026-10-01 with `tipo` on every doc). `firestore.rules` rejects `destacado == true` when `tipo == "persona"`, and the admin form/table disable the destacado checkbox for personas. The public site (`publico.js`) leaves personas out of the marquee (filtering is client-side because `where("tipo", "!=", "persona")` would drop legacy docs without the field) but they DO count in the public total (personas are still clients; the copy must not suggest that only companies are served — hero says "Clientes atendidos"). Personas can also leave a testimonio: the public testimonial hides a persona's own name/logo in the "company" slot (their name is already the author). Caveat: `publicado` is independent of `tipo`, so a published persona is hidden by the site's own code but still readable through the Firestore API — if that matters, set `publicado` to No for personas (or add a rules check). **Deploy `firestore.rules` before importing/saving with `tipo`**, otherwise the writes are rejected (`hasOnlyAllowedFields`).

## Extraction plan (completed, historical)
This was a one-time migration, done in two parts:
1. **Archive → flat HTML** (steps below) — produced 9 standalone `.html` files + `public_gv/` assets. Tables and detailed notes live in [EXTRACTION.md](EXTRACTION.md).
   1. **Map URLs** — list every archive.org page URL to extract (see site map above) in a table.

   4. **Rewrite links** — replace all `web.archive.org/web/.../http://transportesjpgalvez.com/...` links and asset paths in the extracted HTML with the local relative references from the table. This step missed the same wayback-wrapper pattern embedded *inside* the downloaded CSS files' own `url()`/`@import` rules (font-awesome, revolution-slider, bootstrap, etc. — not just the 9 HTML pages) — found and fixed during the Astro migration below.
2. **Flat HTML → Astro source** — the 9 flat files were split into the `src/layouts`/`src/components`/`src/pages` structure described in "Stack" and "Source/dist architecture" above, `public_gv/` moved under `public/`, and the Clientes table's rows (294 at the time, later corrected — see "Known gaps") extracted into `src/data/clientes.json`. 3. **`public_gv/` → `public/images/` by type** (later pass) — the crawl-bucket folders (`imagenes/`, `uploads/`, `web/images/`) and hashed filenames were replaced by the `logos/`/`iconos/`/`fondos/`/`fotos/` structure described in "Assets" above; `public_gv/imagenes/contactenos.png` (an unused variant of the Contáctenos photo, never referenced by any page) was kept and renamed `public/images/fotos/llamenos-alt.png` to match its sibling `llamenos.jpg` instead of being deleted.
